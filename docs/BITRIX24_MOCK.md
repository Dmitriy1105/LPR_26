# Bitrix24 REST-like mock: Банк «Северный контур»

**Назначение:** приближённые к REST-ответам Битрикс24 синтетические данные, созданные из существующего `bank_ml_v2.json`. **Это не настоящая выгрузка из Битрикс24** и не гарантия совместимости с конкретным порталом.

## Поддерживаемые формы ответа

| Метод / сущность | Файл | Записей в полном исходном наборе | Формат |
|---|---|---:|---|
| `crm.item.list`, `entityTypeId=4`, компания | `crm_company_list.json` | 1 | `result.items` |
| `crm.item.list`, `entityTypeId=3`, контакты | `crm_contact_list.json` | 30 | `result.items` |
| `crm.item.list`, `entityTypeId=2`, сделки | `crm_deal_list.json` | 18 | `result.items` |
| `crm.item.list`, `entityTypeId=31`, счета нового типа | `crm_invoice_list.json` | 44 | `result.items` |
| `crm.activity.list`, дела/активности | `crm_activity_list.json` | 540 | `result` (массив) |
| `tasks.task.list`, задачи | `tasks_task_list.json` | 48 | `result.tasks` |

Для списков установлен лимит первой страницы 50 записей; `total` отражает полное число, `next` указывает на следующую страницу, но в этих файлах следующие страницы **не представлены**. Полный набор остаётся в `bank_ml_v2.json`.

## Важные отличия от реального API

1. Для основных CRM-сущностей выбран формат универсального метода `crm.item.list`: `camelCase` и `result.items`. В классических методах `crm.contact.list` / `crm.deal.list` названия полей обычно `UPPER_CASE`. Эти форматы **нельзя смешивать в одном адаптере**.
2. В актуальной документации `crm.item.list` отмечен как устаревающий в пользу REST 3.0 `crm.<тип>.list`. В проекте этот формат используется как учебный совместимый профиль, не как выбор нового промышленного API.
3. `ufCrmMockDueDate`, `ufMockContactId`, `ufMockDealId` — **иллюстративные расширения**, не реальные системные поля. Для реального портала их необходимо заменить полями, найденными через `crm.item.fields` / `crm.<тип>.field.list`.
4. Счета, договоры, платежи и дебиторская задолженность **не тождественны**: фактические оплаты могут храниться в ERP/1С, договоры — в документах или смарт-процессах, а влияние и связи ЛПР — в отдельной системе. Они намеренно не подменяются вымышленными «стандартными» полями.
5. Для `crm.activity.list` и `tasks.task.list` представлены упрощённые демонстрационные ответы. Провайдер, состав полей, привязки, доступность расшифровок и задач зависят от портала, прав, телефонии и версии REST. Наличие текста звонка в фикстуре **не означает**, что Bitrix24 API всегда возвращает расшифровку.
6. Все идентификаторы числовые и связаны с исходными строковыми `personId` / `opportunityId` через `id_mapping.json`. Время — ISO 8601 с часовым поясом; все адреса `.example` и записи синтетические.
