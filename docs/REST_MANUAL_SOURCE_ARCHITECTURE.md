# ТЗ: независимые источники данных для карты ЛПР

## Цель

Разработать систему анализа структуры принятия решений корпоративного клиента на базе двух независимых источников:

1. **Ручная разметка карты** — оценки, роли, связи и комментарии менеджеров, введённые и изменяемые внутри приложения.
2. **Bitrix24 REST** — фактические сведения, извлекаемые из Битрикс24. До подключения портала использовать **синтетические ответы, максимально совместимые с документированными REST-контрактами выбранной версии API**.

После подготовки обоих источников реализовать выбор режима «ручная разметка / REST / смешанный» и ползунок относительного веса свидетельств. Источники **не должны перезаписывать друг друга**.

## Текущее состояние (21.11.2026)

- `src/data/crm.json` содержит демонстрационную карточку контакта **вместе с ручными аналитическими оценками** (`decisionRole`, `stance`, `influence`, `warmth`) и связями. Это пока смешанный внутренний формат, а не независимое хранилище разметки.
- `src/api/crmApi.ts` сохраняет рабочую копию карты и имитацию CRM в localStorage. **Настоящего REST-клиента нет.**
- `src/data/synthetic/bank_ml_v2.json` — нормализованный синтетический набор; содержит также `manualAnnotations` и `relationshipEvents`, поэтому **не является чистым REST-источником**.
- `src/data/bitrix24_mock/` — первая приближённая имитация REST. Она не обеспечивает полного соответствия: смешаны семейства методов, представлены только первые страницы, ряд полей иллюстративен.
- Ползунок смешивания источников **ещё не реализован**.

## 1. Синтетический Bitrix24 REST

**Требование:** данные создаются **сначала по схемам конкретных методов API**, а не путём переименования произвольного внутреннего JSON. Схемы фиксируются с указанием версии API и даты документации. Для каждого метода:

- Точный путь метода, параметры запроса и структура ответа, включая типы, обязательные и nullable-поля, числовые идентификаторы, вложенность, коды статусов и временные форматы.
- Корректные пагинация, сортировка, фильтрация, выбор полей и несколько страниц; клиент должен получать все записи, а не только первую страницу.
- Связи между компаниями, контактами, сделками, пользователями, делами и задачами по **действительным для данного метода** идентификаторам и типам сущностей.
- Варианты пустых полей, отсутствующих данных, удалённых/неактивных контактов, изменения ответственного, дубликатов, ошибок доступа, недоступных прав, лимитов запросов и частичных ответов.
- Раздельные фикстуры для каждого семейства API; **не смешивать** формат универсального `crm.item.list`, классических `crm.contact.list` / `crm.deal.list` и REST 3.0 в одном контракте.
- Пользовательские поля — только с явно заданной схемой и описанием, что их наличие зависит от настройки портала; не представлять `decisionRole`, `influence`, `warmth` как стандартные поля Bitrix24.
- Для звонков/писем/встреч — лишь те сведения, которые реально предоставляет выбранный метод и подключённые интеграции. Тексты, расшифровки и записи разговоров не гарантированы.
- Контракты, оплаты, задолженность и внутренние переписки клиента **не считать автоматически доступными** через стандартный CRM REST. Если они нужны в ML, оформить отдельные **дополнительные** синтетические источники (ERP/1С, документооборот, почта) с собственным provenance.
- Все записи демонстрационные, без реальных персональных данных; текстовые данные явно маркируются `synthetic` на уровне метаданных фикстуры, но не добавляются как вымышленные поля в REST-объект, если API их не допускает.

**Контроль качества:** schema/contract-тесты по каждому методу, тесты пагинации, ID и внешних ключей, проверка повторяемости генерации, тесты адаптера на реальные документированные примеры и ошибки API. Совместимость с конкретным порталом подтверждается только интеграционным тестом, не синтетическими фикстурами.

## 2. Независимая ручная разметка

Отдельное хранилище `manual_annotations` и `manual_relations`. Рекомендуемые поля:

| Поле | Значение |
|---|---|
| `annotationId` | ID записи |
| `companyId`, `personId` | Ссылка на сущность карты через слой сопоставления |
| `field`, `value` | Роль, позиция, влияние, теплота, отношение, связь |
| `authorId` | Автор оценки |
| `observedAt`, `recordedAt` | Когда наблюдали и когда внесли |
| `confidence` | Уверенность автора, не вероятность ML |
| `evidenceIds` | Ссылки на подтверждающие факты |
| `status`, `revision` | Актуальность и история исправлений |
| `source` | Всегда `manual` |

Изменения менеджеров не должны попадать в RAW-ответы Bitrix24. Изменение оценки вручную не должно менять исходные REST-данные. Сохранять автора и историю правок.

## 3. Общая модель и provenance

Для каждого нормализованного факта сохранять: `factId`, `entityId`, `field`, `value`, `sourceType`, `sourceRecordId`, `observedAt`, `ingestedAt`, `confidence` (если применимо), `evidenceIds` и версию адаптера. `sourceType`: `manual`, `bitrix24`, `external`, `derived`.

Слой Entity Resolver связывает `bank-p0` с числовым CRM ID и поддерживает случаи, когда ручной контакт ещё не найден в REST или есть неоднозначное совпадение. **Не объединять людей только по совпадению ФИО.** При конфликте фактов показывать оба источника, время, автора и причину расхождения.

## 4. Будущий ползунок источников

Режимы:

- **0% REST / 100% ручная разметка** — только оценки и свидетельства ручного источника.
- **50% / 50%** — комбинированная оценка при наличии сопоставимых свидетельств.
- **100% REST / 0% ручная разметка** — только признаки, извлечённые из REST-данных, и соответствующие модельные выводы.

Ползунок **не смешивает JSON-объекты и не изменяет исходные записи**. Он задаёт вес **сопоставимых оценок**, например влияние, поддержка инициативы, риск потери контакта. Для нормированных оценок одного показателя допустим базовый вариант:

`score = (w_manual * score_manual + w_rest * score_rest) / (w_manual + w_rest)`

где веса нормируются **по реально доступным** источникам; если источника нет, это отмечается явно, а не подставляется ноль. Для фактов вроде даты договора, суммы платежа или должности нельзя применять арифметическое усреднение — используется правило приоритета источника, проверка даты/достоверности и отображение конфликта. Для графовых связей требуется отдельная политика объединения и весов.

Каждый результат показывает доли источников, число свидетельств, временной интервал, доверие, ключевые подтверждения и предупреждения о расхождениях. Ползунок меняет визуализацию и вычисляемые оценки, но **не переобучает ML на лету**. Если нужен прогноз, зависящий от веса источников, модель должна быть спроектирована и проверена для такого входа.

## 5. Этапы реализации

1. **Сначала:** выбрать версию Bitrix24 REST, создать каталог API-контрактов и генератор полноценной синтетической выгрузки по методам, включая все страницы, тестовые ошибки и валидацию.
2. **Затем:** вынести текущие ручные оценки и связи из `CRMData` в самостоятельный store без потери истории и функций редактирования.
3. Реализовать адаптер REST → нормализованные факты, таблицу сопоставления ID и provenance; подключить синтетические данные к карте в режиме «только REST».
4. Сопоставить признаки двух источников, определить обработку конфликтов и недостающих данных.
5. **После этого:** реализовать переключатель и ползунок 0–100%, динамический пересчёт и объяснения на карте.
6. Подключить и оценить ML; исключить утечку будущих данных, разделить обучение и тест по времени/сценариям.

## Критерии приёмки первого этапа

- Для каждого выбранного метода указаны версия API, документация, схема запроса и ответа.
- Генератор воспроизводимо создаёт корректные многостраничные ответы и связанные сущности.
- Ни одно ручное аналитическое поле не выдаётся за стандартное поле REST.
- Исходный `crm.json` и функциональность ручной карты не ломаются до отдельной миграции.
- Тесты схем, ID, пагинации и адаптера выполняются; ограничения совместимости документированы.

**Важное ограничение:** имитация API может быть максимально близкой к документации, но стопроцентную совместимость можно подтвердить только на тестовом портале Битрикс24 с нужной конфигурацией, правами и интеграциями.
